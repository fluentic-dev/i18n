# How messages and translation fit together

Write a message where it belongs in your code. Fluentic's message APIs are also the markers that tell the CLI which strings should be translated:

```tsx
import { t } from '@fluentic/i18n';

export function SaveButton() {
  return <button>{t.jsx('Save changes')}</button>;
}
```

The same rule works wherever a message appears:

- use `t.jsx()` inside JSX;
- use `t.text()` when you need a plain string;
- use `t.msg()` when you need to define a message before using it.

All three forms can be recognized by the extractor when the message is a source literal. You do not need to create a separate key or register every message in a central configuration first.

## From a message to a catalog

The CLI recognizes these calls precisely and records the source message, context, notes, and stable ID:

```ts
t.jsx('Save changes');
t.text('Welcome, {name}!', { name: 'Ada' });
t.msg('You have {count, plural, one {# message} other {# messages}}', {
  count: Number,
});
```

After [installing the CLI and adding the `i18n` script](../cli/overview#1-add-a-config-file), run extraction to create the source list:

```sh
pnpm i18n extract
```

Extraction only finds and records messages. It does not decide whether a translation should come from an automatic service or a person.

## Translate automatically when it helps

The CLI can call configured translation services for messages that do not yet have a translation in the target language. Google Translate and DeepL integrations are available, and `defineTranslator()` lets you connect another service.

See [translation providers](../cli/translators) for configuration and provider behavior.

Automatic translation is optional. With a provider configured, `translate` processes missing messages from the current extraction for each configured target. Omit the provider to use only manual translations.

## Translate manually

A team can supply every translation manually and never configure a provider. After extraction, run `merge` to create the records, then edit `manual.jsonl` or import translations from an external tool. Run `merge` again to rebuild the runtime catalog; non-empty manual translations take priority.

The CLI keeps automatic and manual translations separate:

- `manual.jsonl` contains translations written or reviewed by people;
- `auto.jsonl` contains results returned by an automatic provider;
- `merged.jsonl` is generated from both and is the file your app loads.

Do not edit `merged.jsonl` directly; it is regenerated by the CLI.

## Why the catalog uses JSONL

JSONL is intentional. Each message record occupies one line with a stable ID, so unrelated changes from multiple developers are easier for Git to merge than changes to one large JSON object. Conflicts can still happen when two people edit the same message, but unrelated messages stay independent.

Editing JSONL by hand is not always convenient. Use the CLI's export and import converters when your team prefers another tool or needs to send files to translators or translation services. Converter callbacks can exchange formats such as JSON, CSV, PO, and XLIFF; these converters are not bundled. Use them to export records for review and import the edited translations into the manual layer.

See [catalog formats and converters](../cli/formats) for the supported converter API and file-preservation rules.

## Define before you render

Messages often need to be defined in a constant, shared package, business logic, navigation config, or validation rule before a component knows how to display them. Use `t.msg()` for that case:

```ts
const welcome = t.msg('Welcome, {name}!', { name: String });
```

Render it later as JSX or a string:

```tsx
t.jsx(welcome, { name: 'Ada' });
t.text(welcome, { name: 'Ada' });
```

The message is resolved in the current language at render time, and its params remain type-checked at each call site.

## Add context when identical text differs

Source text is the default message identity. If the same words mean different things in different places, add context:

```tsx
t.context('checkout').text('Continue');
t.context('onboarding').text('Continue');
```

The text remains natural in source code while the extractor records two distinct translation entries.

## Load the generated catalog at runtime

The runtime only needs a loader that returns the generated catalog for the selected language:

```ts
import { I18nManager } from '@fluentic/i18n-web';

I18nManager.configure({ languageId: 'en' });
I18nManager.setTranslationLoader(async ({ languageId }) => {
  if (languageId === 'en') return [];
  const response = await fetch(`/i18n/${languageId}.jsonl`);
  if (!response.ok) throw new Error(`Catalog request failed: ${response.status}`);
  return response.text();
});
await I18nManager.init();
```

Publish each target language’s `merged.jsonl` at the matching URL in your build or deployment step. The CLI does not copy catalogs to public URLs.

Then switch languages through `I18nManager`. `t.jsx()` updates JSX output automatically. When a React component uses `t.text()` for string output, call `I18nState.use()` if that string should update after a language change.

See [loading catalogs](../runtime/loading) and [runtime language management](../runtime/manager) for loader and language setup.
