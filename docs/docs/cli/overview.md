# Extract and translate messages

The CLI keeps three things separate:

- your source code, where messages are written;
- translations you or a translator edit by hand;
- translations generated by an automatic provider.

You do not edit the final catalog directly. The CLI rebuilds it from the separate layers whenever you run `update`.

## The flow in one picture

```text
source files
    │ extract changed files; synchronize current messages
    ├──────────────► translations/meta.jsonl        shared notes and metadata
    ├──────────────► translations/fr/manual.jsonl   human translations
    └──────────────► translations/fr/auto.jsonl     provider translations
                              │ merge: manual wins when both exist
                              ▼
                    translations/fr/merged.jsonl

cache.local/{hashes,extract}.json
    local per-file extraction cache; safe to delete
```

`merged.jsonl` is the default file your application loads. Set [`catalogFormat`](./configuration#catalog-output-formats) to generate JSON, CJS, or MJS catalogs instead or alongside it. `manual.jsonl` and `auto.jsonl` are the files the CLI uses to produce them.

These files use JSONL deliberately: one message tuple per line. Context and source text form the identity; no generated ID is stored in authoring files. When two branches update different messages, Git can usually merge those lines independently.

After resolving conflicts in the authoring JSONL files, run `pnpm i18n conflict` to regenerate all configured catalog formats. The command stops if an authoring file still has conflict markers or invalid records. Stage the resolved files in Git after reviewing them.

## 1. Add a config file

Install the CLI and add a script so you do not have to repeat the config path:

```sh
pnpm add -D @fluentic/i18n-cli
```

```json title="package.json"
{
  "scripts": {
    "i18n": "fluentic-i18n --config i18n.config.ts"
  }
}
```

Create the config:

```ts title="i18n.config.ts"
import { defineConfig } from '@fluentic/i18n-cli';

export default defineConfig({
  languages: {
    source: 'en',
    targets: ['fr', 'de'],
  },
  files: {
    includes: ['src/**/*.{ts,tsx,js,jsx}'],
    excludes: ['**/*.test.*', '**/*.spec.*'],
  },
});
```

`source` is the language used in your code. `targets` are the languages for which the CLI maintains translation files.

## 2. Understand extraction

When your code contains a message:

```ts
import { t } from '@fluentic/i18n';

t.jsx('Welcome back!');
t.text('Hello, {name}', { name: 'Ada' });
t.msg('You have {count} messages', { count: Number });
t.context('checkout').note('Primary payment action').text('Continue');
```

the extractor finds those literal message calls. It writes shared notes and structured metadata once to `translations/meta.jsonl`, then synchronizes `[message, translation]` and `[context, message, translation]` tuples in every target language. Existing translations with matching context and source text are preserved; obsolete messages are removed.

To avoid reparsing unchanged source, it maintains two disposable local files:

```text
i18n/data/cache.local/
├── hashes.json    # source modification times and content hashes
└── extract.json   # messages grouped by source file
```

Ignore `cache.local` in version control. Deleting it affects only extraction speed: the next extraction rebuilds it from source. Merging never reads this cache.

`t.jsx()`, `t.text()`, and `t.msg()` are extraction markers. Use the named import `t` from `@fluentic/i18n` or `@fluentic/i18n/core`, and literal strings or template literals without interpolations. The extractor does not follow renamed imports, variable aliases, or scopes saved in variables. Inline `context()`, `note()`, and `meta()` chains are supported; see [metadata](../learn/metadata).

A dynamic source passed to `t.msg()` fails extraction; a non-literal message argument to `t.jsx()` or `t.text()` is skipped. The special `t.jsx(() => element)` callback is a reactive boundary rather than a message, so the outer call is ignored while literal `t.text()`, `t.jsx()`, and `t.msg()` calls inside its callback are extracted normally. Reused descriptors are extracted at their literal `t.msg()` definition.

Extraction does not call an automatic translation provider or write runtime catalogs. It updates the authoring translation layers directly.

Run extraction alone when you want to synchronize source messages without translating or rebuilding runtime catalogs:

```sh
pnpm i18n extract
```

## 3. Understand the translation files

Run merge after extraction or manual translation edits:

```sh
pnpm i18n merge
```

For each target language, the CLI creates:

```text
i18n/data/translations/
├── meta.jsonl
└── fr/
    ├── manual.jsonl
    ├── auto.jsonl
    └── merged.jsonl
```

`meta.jsonl` is the language-independent source list. Its rows are `[message, metadata]` or `[context, message, metadata]`. Translation rows are `[message, translation]` or `[context, message, translation]`. `manual.jsonl` is for translations written or reviewed by people; `auto.jsonl` is for provider results. `merged.jsonl` combines both, with a non-empty manual translation taking priority.

For a manual-only workflow, leave `translator` unset, fill the last tuple value in `manual.jsonl`, and run `merge` again. Do not edit `merged.jsonl`; it is regenerated.

Review wording and ICU behavior in your app. To retain an approved provider translation as a manual override, copy its translation into the matching manual record. The CLI has no review or approval command.

Extraction keeps only identities currently present in source. Removing a message or changing its source text or context removes its old metadata and translation rows on the next extraction. Merge reads `meta.jsonl` and the translation files, so it works on a clean checkout without source extraction or a local cache.

## 4. Automatically translate missing messages

Automatic translation is optional. The CLI only sends a message to a provider when that target language has no non-empty translation for it in either `manual.jsonl` or `auto.jsonl`. Existing manual translations are never sent for replacement.

### Keep provider keys in env files

By default, the CLI looks beside the selected config file for:

```text
i18n.env          # shared values or safe defaults
i18n.env.local    # local secrets and overrides
```

`i18n.env.local` overrides `i18n.env`. Values in `process.env` override both. A relative `env` path is resolved from the directory containing `i18n.config.ts` or `i18n.config.js`.

```env title="i18n.env.local"
DEEPL_API_KEY=your-key
GOOGLE_TRANSLATE_API_KEY=your-key
```

Keep `i18n.env.local` out of version control. You can select one custom file with `env: 'secrets/translation.env'`, or disable env-file loading with `env: false`.

### Option A: Google Translate

Google Cloud Translation uses `GOOGLE_TRANSLATE_API_KEY` by default:

```ts
import { defineConfig } from '@fluentic/i18n-cli';
import { createGoogleTranslator } from '@fluentic/i18n-cli/translators';

export default defineConfig({
  languages: { source: 'en', targets: ['fr'] },
  translator: createGoogleTranslator(),
});
```

You can provide the key directly, although an env file is safer:

```ts
translator: createGoogleTranslator({ apiKey: 'do-not-commit-this' });
```

Or choose the env key explicitly:

```ts
translator: createGoogleTranslator(({ env }) => ({
  apiKey: env('MY_GOOGLE_KEY'),
}));
```

### Option B: DeepL

DeepL uses `DEEPL_API_KEY` by default and the DeepL Free endpoint:

```ts
import { defineConfig } from '@fluentic/i18n-cli';
import { createDeepLTranslator } from '@fluentic/i18n-cli/translators';

export default defineConfig({
  languages: { source: 'en', targets: ['fr'] },
  translator: createDeepLTranslator(),
});
```

The same key options are available:

```ts
translator: createDeepLTranslator(({ env }) => ({
  apiKey: env('MY_DEEPL_KEY'),
}));
```

### Option C: your own translator

Use a custom translator for another provider or an internal service. The CLI gives it the untranslated records and an `env()` helper:

```ts
import { defineConfig, defineTranslator } from '@fluentic/i18n-cli';

export default defineConfig({
  languages: { source: 'en', targets: ['fr'] },
  translator: defineTranslator({
    batch: 50,
    tag: false,
    translate: async ({ items, sourceLanguageId, targetLanguageId, env }) => {
      const response = await fetch(env('TRANSLATION_SERVICE_URL'), {
        method: 'POST',
        headers: {
          Authorization: `Bearer ${env('TRANSLATION_SERVICE_KEY')}`,
          'Content-Type': 'application/json',
        },
        body: JSON.stringify({ items, sourceLanguageId, targetLanguageId }),
      });
      if (!response.ok) throw new Error(`Translation failed: ${response.status}`);
      return response.json(); // Array<{ id: string; translation: string }>
    },
  }),
});
```

`env(name)` throws when the requested value is missing, so a missing secret fails clearly instead of sending a broken request.

## 5. Run the complete update

With the config in place, run this with or without a provider:

```sh
pnpm i18n update
```

`update` performs the complete flow:

1. incrementally extract changed source files and update both authoring layers;
2. preserve matching translations and remove obsolete records;
3. if a translator is configured, request only messages missing from both layers;
4. write new provider results to `auto.jsonl`;
5. rebuild the runtime catalog from translation files alone.

Run it again whenever messages change. Matching manual translations are retained. After manual edits or imports, `merge` alone is enough because it reconstructs catalogs directly from the translation authoring files.

## Other commands

| Command                        | What it does                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------- |
| `pnpm i18n update`             | Extract, translate missing messages, and rebuild catalogs                             |
| `pnpm i18n extract`            | Incrementally synchronize source messages into the translation authoring files        |
| `pnpm i18n merge`              | Rebuild runtime catalogs from translation files only; no source scan or provider call |
| `pnpm i18n translate`          | Translate missing messages; run `merge` afterward                                     |
| `pnpm i18n export <converter>` | Export readable translations through a built-in or configured converter               |
| `pnpm i18n import <converter>` | Import records into the manual layer; run `merge` afterward                           |

JSON, CSV, XLIFF, and `handoff` exchange are built in; use `--output <folder>` for export and `--input <folder>` for import. Add or override formats with [import/export converters](./formats). Publish `merged.jsonl` and configure a [runtime loader](../runtime/loading) separately; the CLI does not load catalogs into your app.

For detailed configuration, see [CLI configuration](./configuration). For provider behavior and custom translators, see [Translation services](./translators).

## Command output and troubleshooting

Commands use colored `RUN`, `DONE`, `INFO`, `WARN`, and `ERROR` tags, aligned details, and elapsed times. Paths are shown relative to the working directory when shorter. Use `--verbose` (or `-v`) for individual files and translated message IDs. Color is automatic for terminals and disabled in redirected output; `--no-color` or `NO_COLOR` disables it, and `FORCE_COLOR=1` enables it. Extraction reports matched files, cache hits, parsed files, files with no translatable messages, removed files, unique messages, target languages, output location, and elapsed time. A cached run still reports the message total. No matching files or no translatable messages produces a warning with the relevant config fields to check.

The config line is flush left, phase details are indented, and every `DONE` line has a blank line above it. The entire CLI invocation also ends with exactly one empty line on success, help, or failure. Nested stages do not add an exit separator. INFO text aligns with detail values, and provider failures show the step, language pair, provider, HTTP status, reason, and next action on separate rows. Handoff displays locale counts, input/output locations, and a copyable `GUIDE` block without repeated log prefixes. Repair guidance uses the same block layout on stderr; paths inside agent instructions remain absolute. Identical-source warnings are grouped by locale, with affected keys available through `--verbose`. Translation reports progress before provider requests. Suggested next steps appear before completion and are omitted for no-op imports and stages already handled by `update`. Usage errors use the same `ERROR` format as command failures.

Merge reports translated and missing counts per language and the generated catalog location. Translation explains when no provider is configured or no messages need translation, and reports translated and remaining counts. Import and export report language/file counts and the exchange folder. `conflict` rebuilds catalogs after you resolve authoring-file conflicts; `update` reports each stage.

Failures go to stderr with the command name and a readable explanation, and exit with status 1. Unknown formats list built-in and configured converters. Config and callback validation identify the field or language involved. Warnings (such as an unsupported language pair) do not fail the command; check the remaining-message counts.

Normal errors omit stack traces. To troubleshoot a failure in a custom callback, enable technical details explicitly:

```sh
pnpm i18n --debug translate
```

Programmatic APIs still reject with errors so callers can handle them. Reporter `phase:end` events may include a `summary` and labeled `details`; the console displays details when provided. `createConsoleReporter(write, writeError, { color, verbose, cwd })` lets you control presentation and send warnings and errors to a separate stream. Info events can include labeled `details` or a copyable `block`, while retaining a readable `message`. Custom reporters still receive every file and translated-message event.

## Read-only lint checks

```sh
pnpm exec fluentic-i18n lint
pnpm exec fluentic-i18n lint --strict
```

`lint` scans the configured source files without using or writing the extraction cache. It checks `meta.jsonl` and every target language's `manual.jsonl` and `auto.jsonl`, reports diagnostics with rule codes and locations, and summarizes translation coverage. It does not generate translations, invoke providers, or write catalogs. As with other commands, loading the config executes your config module.

Errors include invalid source/ICU syntax, malformed catalog rows, duplicate identities, translations without metadata, conflicting source metadata, and incompatible translation structures. ICU comparison checks arguments, tags, formatting styles, select keys, plural type, offset, and exact-number cases, while allowing language-specific plural categories.

Source checks reuse the compiler's import, alias, and context resolution:

```tsx
// Error: missing runtime parameter.
t.jsx('Hello {name}');
// Correct:
t.jsx('Hello {name}', { name: user.name });

// Warning: missing descriptor schema entry.
t.msg('Hello {name}');
// Correct:
t.msg('Hello {name}', { name: String });
```

Checks also cover nested parameters, missing rich-text handlers, extra keys, schema constructors passed as rendering values, and obviously incompatible literal values for numeric/date parameters. `{break}` is supplied by the runtime. Rich-text handlers are not required in primitive descriptor schemas.

Use `lint.parameterChecks` to control parameter and descriptor schema diagnostics:

```ts
lint: {
  parameterChecks: {
    msg: false,
    jsx: {
      skip: [
        { match: 'exact', terms: 'Legacy {name}' },
        { match: 'contains', terms: ['Debug', 'Internal'], caseSensitive: false },
        ({ message }) => message.startsWith('Test'),
        { check: ({ message }) => message.startsWith('Preview') },
      ],
    },
    text: true,
    translation: {
      skip: ({ message, translation }) => message === 'Legacy {name}' && translation === 'Legacy',
    },
  },
}
```

`true` (the default) enables all parameter checks; `false` disables them all, including translation structure comparison. A map controls `msg`, `jsx`, `text`, and `translation` individually; omitted checks remain enabled. Each entry accepts a boolean or `{ enabled?, skip? }`. `enabled` defaults to `true`; `enabled: false` bypasses the check without calling `skip`. `skip` accepts one rule or an array. A rule can be `{ match: 'exact' | 'contains', terms: string | string[], caseSensitive?: boolean }`, a direct predicate, or `{ check: predicate }`. Matching uses the same implementation as `forbiddenMessages`. String rules always match the source message, including for translation checks. Exact matches compare the entire ICU string; contains matches substrings. Matching is case-sensitive by default.

Rules run in order: any matching rule or predicate returning `true` skips the check and short-circuits later rules. If none matches, including an empty rule array, the check runs. A thrown or invalid callback result reports an error and stops that check's rule evaluation. Skip rules do not accept diagnostic `id`, `severity`, or `message` fields. Unlike `forbiddenMessages` callbacks, which return diagnostic text, skip callbacks return booleans.

The `msg`, `jsx`, and `text` predicates receive `{ message: string }`, containing the ICU source message. The `translation` predicate receives `{ message: string, translation: string }`, with the catalog row's source and translated ICU strings. Translation predicates run for each non-empty, syntactically valid authoring row in both manual and automatic layers. Predicates are synchronous; throwing or returning a non-boolean produces a `parameter-check-error` while other checks continue. The top-level `parameterChecks` accepts only a boolean or the four-check map, never a top-level `{ enabled, skip }` object.

Source switches cover missing/unused parameters, incompatible literal types, missing/incompatible descriptor schemas, and schema constructors passed as rendering values. The translation switch controls the full ICU structure comparison, including arguments, tags, select keys, plural offsets, and formatting styles. Source and translation ICU syntax, catalog row validity, extraction, forbidden-message rules, and coverage checks remain enabled even when parameter checks are disabled or skipped. Keep custom predicates read-only.

Missing metadata, extraction drift (new/removed messages or changed notes/metadata), unused parameters, and missing or incompatible schema entries produce warnings. Errors exit with status 1; `--strict` also fails on warnings. Incomplete translation coverage is informational and does not fail either mode.

Optional project-specific terms can be kept out of source messages:

```ts
export default defineConfig({
  languages: { source: 'en', targets: ['fr'] },
  lint: {
    forbiddenMessages: [
      { match: 'exact', terms: 'Acme' },
      { match: 'contains', terms: ['WhatsApp', 'Booking.com'], caseSensitive: false },
      {
        id: 'custom-wording',
        severity: 'error',
        check: (icuMessage) =>
          icuMessage.includes('internal-only')
            ? 'Remove internal wording from this message.'
            : undefined,
      },
    ],
  },
});
```

`forbiddenMessages` accepts one rule or an array of rules. `terms` also accepts a single string or an array. `exact` matches the entire ICU source string; `contains` matches a substring anywhere in it, including ICU arguments and branch text. Matching is case-sensitive unless `caseSensitive: false`. Rules default to warnings; set `severity: 'error'` to fail lint without `--strict`. An optional `message` replaces the built-in diagnostic for a matching rule, and `id` identifies the rule in diagnostics. No product names are forbidden by default.

A callback can be provided directly (`forbiddenMessages: (icuMessage) => ...`) or as a rule's `check` property. It receives the complete ICU source string and returns a diagnostic string, an array of diagnostic strings, or `undefined` when valid. Async callbacks are supported. Callbacks run once per context/source identity across extracted and catalog-only messages. Exceptions and invalid return values produce rule-execution errors while other checks continue. Callbacks are trusted configuration code; keep them read-only to preserve lint's read-only behavior.

The earlier `forbiddenTerms` option is replaced by `forbiddenMessages: { match: 'contains', terms: [...] }`.

Static analysis checks literal messages and inline parameter/schema objects. Dynamic objects, spreads, computed keys, descriptor rendering, and callbacks are not fully validated; this is not a replacement for TypeScript or runtime tests. Structure comparison uses sets, so repeated-placeholder counts and every change in nesting or branch placement are not checked. Lint does not assess translation quality or validate generated merged catalogs.

Programmatic callers can use `await lint(config, reporter?)` to receive diagnostics, error/warning counts, file/message totals, and coverage by locale. The function returns findings without throwing; configuration, source-root, and file-discovery failures can still throw.
